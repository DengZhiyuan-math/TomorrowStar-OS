## Question

首版如何从已有申请记录中显式选择一批岗位，并将执行进度写回同一份记录？

决定批次入口、允许状态、岗位标识、附件选择和版本绑定。明确原笔记、worker 运行
记录与答案库分别拥有哪些字段。决定门户、Obsidian 与 worker 同时更新时的单一写入
路径与冲突处理，不把当前进程内 RLock 当成多进程锁。

## Evidence and assets

- `src/career_evidence_graph/application_automation.py` 的岗位规范化、重复检查和 revision 检查。
- `src/career_evidence_graph/career_portal_data.py` 的原记录编辑、备份与冲突检查。
- [现有接入的数据约定](../../../docs/application-automation.md)。

## Resolution requirements

先检查已有接口。给出一个合成批次的输入契约和写回所有权表。
填完、待用户处理、已人工提交及已核验接收必须有不同含义。
附件对外发送范围应在批次准备时具体呈现，避免运行时反复询问已确认范围。

## Answer

### 批次入口与检查

在求职进度中勾选已有申请记录创建批次，不复制原申请记录。
首版复用现有 drafting（准备投递）状态、Lever / Greenhouse 直接岗位链接识别、
链接规范化和重复岗位检查。勾选不等于执行或提交。
批次准备展示公司、岗位、链接、状态与逐岗位附件；启动时绑定并检查输入版本。
原记录身份来自已有 application ID，不能只用显示名称定位。

每个岗位分别选择具体简历文件，不设置批次默认简历或跨岗位继承选择。
同一文件可以被用户分别选择给多个岗位。`resume_version` 是说明，不能取代文件内容版本。
缺少选择、文件不可读或内容变化时，该岗位等待处理，不能自动改用其他文件。
其他附件不因选择简历而获得发送范围；批次准备应具体展示本次目标与已选资料。
启动后只执行已确定的目标和资料范围；最终 Submit 仍由用户操作。

### 最小输入契约

| 输入 | 来源与绑定 | 验证要求 |
| --- | --- | --- |
| 批次身份及勾选项 | 私人 worker 运行记录，引用已有申请 ID | 无重复项，不创建第二份岗位记录 |
| 申请 ID 与原笔记 revision | 原记录读取结果 | 启动、恢复和写回时核对 |
| 公司、岗位、规范化 URL、ATS、申请状态 | 原记录和已有链接识别逻辑 | 只处理 drafting 的受支持直接岗位 |
| 每个岗位的所选简历与内容版本 | 用户逐岗位选择，内容摘要绑定具体文件 | 不猜路径、不继承；变化后暂停对应任务 |
| 本次资料发送范围 | 批次准备中呈现的目标、所选资料及答案库契约 | 不因网页内容扩大目标、附件或最终提交动作 |
| 运行进度与待同步结果 | 私人 worker 状态 | 不复制申请答案值或替代原记录的申请状态 |

合成示例：记录 A / B 各保留自己的 ID 与 note revision；用户分别选简历 A / B，
运行输入分别绑定其文件摘要。A 缺失回答时，A 的 next_action 可同步为“需要补充”；
B 填写完成时，B 的 next_action 可同步为“待复核”。两条记录仍为 drafting。
是否继续处理 B 由[确定任务暂停、恢复、取消与去重语义](05-recovery-cancellation.md)决定。

### 所有权与自动写回

| 数据 | 规范来源 | worker 权限 |
| --- | --- | --- |
| 岗位身份、公司、URL 和用户职业事实 | 原申请记录、用户已确认资料 | 读取并绑定，不从页面或猜测改写 |
| 所选简历内容版本 | 用户逐岗位选择的文件 | 核验并使用本次选择，不生成或改写简历 |
| 申请答案和适用范围 | 同一份申请答案库 | 按已解决答案库契约读取及保存 |
| 领取、填表、等待、待复核、待同步 | 私人 worker 运行记录 | 持久化实际进度，门户按申请 ID 展示 |
| 下一步行动 | 原记录 `next_action` | 自动同步与实际进度相关的待办，保留其他用户内容 |
| 已投递 / 已确认收到 | 原记录 `status` | 只按对应真实提交确认及接收证据更新 |
| 原字节与修改历史 | 原记录备份机制 | 保留，不能用自动同步覆盖历史 |

填表完成、按钮点击或 worker 成功退出均不能证明投递或招聘方接收。
用户明确确认提交完成且结果无歧义，才可更新 applied；接收证据核验后才可更新
confirmation_received。结果不明时同步待核实行动，不自动重试最终提交。
用户对提交的报告与 ATS 接收证据保留不同来源，不能相互替代。

门户与 worker 的系统写入使用同一受控串行入口或共享锁协议，并复用原记录更新、
expected revision 检查、原字节备份和原子替换。现有进程内 RLock 不构成该跨进程能力。
检测到用户或 Obsidian 变更时，停止本次写回并保留待同步结果，重新读取后再处理。
不能把现有 revision 复查描述成外部编辑器已参与的共同锁或完整事务；
具体协调与故障窗口须在运行时、恢复决策和实现验收中处理。

本系统成功写回后，将绑定 revision 更新为该写回结果的 revision，避免自己的
next_action 更新被当成外部输入冲突。外部变更不能以此方式跳过检查。
写回失败不回退浏览器执行结果，也不触发重复填写或提交；按恢复票重试同步。
不要用现有 `notes` 字段覆盖用户的 Hermes Notes 来存运行日志。

### 验收要求

- 只处理用户勾选且满足检查的原记录；未选记录不进入批次。
- A / B 逐岗位选择不同简历，绑定及回读必须对应各自文件；没有批次默认值。
- 填写完成后 next_action 自动同步为待复核，status 不因填表变成 applied。
- 原笔记并发变化时不强行写回；待同步结果保留且不导致重复执行。
- worker 自己的受控同步更新绑定 revision，不造成无意义的重复确认。
- 已投递与已确认收到分别依赖对应确认来源，结果不明不伪报成功。

这些是开发契约和验收要求，不是独立 worker 已通过的验证结果。
