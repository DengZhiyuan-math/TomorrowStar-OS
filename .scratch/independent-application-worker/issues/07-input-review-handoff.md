## Question

用户怎样集中补充未知问题、确认答案适用范围，并找到各岗位待复核的真实页面？

用一个合成批次展示：缺失问题汇总、用户回答、保存范围、多个相同问题合并、恢复
提示、资料修改导致失效、待人工提交和接收记录。优先现有门户界面，不先建设新产品。

区分保存答案、发送申请资料和人工最终提交。原型不能上传真实资料或操作真实 ATS。

## Answer

### 界面结构

在现有求职进度中呈现 A 布局，不另建控制应用。
左侧集中补充未知问题；右侧按原申请 ID 展示各岗位进度、所选简历及复核入口。
窄屏按相同顺序堆叠两区，不要求左右双栏始终同时可见。
批次暂停／继续及信息库入口位于两区上方。

```mermaid
flowchart LR
  Q[左侧：补充项与实际适用范围] --> S[保存确认答案]
  S --> R[重查相关等待岗位]
  R --> J[右侧：岗位进度与独立简历]
  J --> B[打开该岗位的真实复核页面]
  B --> U[用户编辑及最终提交]
```

### 补充项与信息库

一个补充项显示题目、必要条件、受影响岗位、系统提出的默认范围和用户答案输入。
只有等价且条件一致的问题可以合并；国家、当前／未来、资格／担保及选项含义仍分别检查。
用户可以查看网站原问题，不要求其识别内部字段名称。
范围可以有默认值；个人答案不得预填模型猜测值或隐式 Yes／No／0。

默认保存到同一答案库，并按实际范围复用。用户只修改范围例外。
选择“仅本次”时明确用于哪个岗位，不把合并项的所有岗位都当成“本次”。
保存成功后重查等待岗位：全部条件满足且批次运行时自动恢复；缺其他输入时继续等待。
整批暂停时显示“已就绪，等待继续”，保存答案本身不解除批次暂停。
保存失败时保留本次输入并显示原因，不把未保存值标成已确认可复用答案。

信息库提供查看、修改适用范围、修改答案和撤回入口。
修改或撤回使使用旧版本的计划失效；已交接页面显示需要重新核验，不覆盖用户的人工编辑。
新的系统等价关系与用户确认的个人答案保留不同来源。

### 单岗位进度与复核

| 岗位区域显示 | 含义与动作 |
| --- | --- |
| 公司、岗位、平台与原记录 | 定位用户已经选择的同一申请，不创建第二份记录 |
| 简历文件和具体版本 | 每岗位独立选择；缺失或变化时只让相关岗位重新核验 |
| 补充等待 | 显示相关补充项；其他就绪岗位可以继续 |
| 已就绪但批次暂停 | 等待用户恢复批次，不暗示浏览器正在填写 |
| 页面容量等待 | 保留待复核页面，等待用户释放容量；不误报为未知答案 |
| 待人工复核 | 打开专用浏览器中该岗位的真实页面；交接后该页无自动执行权 |
| 页面失效或输入版本变化 | 显示具体原因，按既有恢复契约重查；旧页面不自动标记已恢复 |
| 待同步或记录冲突 | 独立显示执行进度与原记录状态；保留待写回结果，仅重试同步 |
| 人工已提交／已核验接收 | 分别显示对应来源；填表完成不能代替任一确认 |

复核入口不使用旧截图或 DOM 快照代替真实申请页面。
用户可在真实页面修改答案并最终提交。暂停批次不阻止已经交接页面的人工处理。
只在用户明确重新接管并重新核验后，worker 才能再次处理已交接页面。
人工提交报告与 ATS 接收证据分别记录；看不到接收结果时显示待核实，不重试提交。

### 页面与检查边界

正式界面不暴露运行日志、工具命令或后台技术状态，除非这些信息用于解决当前阻塞。
重连后先显示已保存进度和暂停状态；不自动重启整批。
页面关闭检测、版本与写回守卫复用已解决的运行时和恢复契约，原型不另定义这些规则。

用户选择 A 是布局决策。已完成 JavaScript 语法及文档链接检查；浏览器交互检查未完成。
开发验收还须覆盖键盘、窄屏、保存失败、范围例外、仅本次、暂停、版本变化、冲突和真实页面交接。
当前演示全部使用合成内存数据，正式版本须接入既有受控后端并完成这些检查。
