# 经历 JSON、来源导入与派生目录操作

现有 `CareerLibrary`、`ExperienceStore` 和 CLI 已支持 J03 结构化经历。
`save_experience`、`read_experience`、`sync_experiences` 继续复用明确选择的职业库
manifest、`candidate_id`、来源关系和写入锁；新增导入动作也使用同一个存储。
基础信息库通过现有 `career_library` 字段提供目录，不复制经历全文。

J03 初始源码验证使用合成数据，当时未迁移真实私库或更新安装版，也不代表
J04–J08 已经完成。后继存量整理状态见下节。简历输出统一为英语，使用 LaTeX
默认字体；职业原始资料可保留原语言。

## 职业经历库整理标准 — 2026-10-25

职业经历库维护经过整理、可复用的职业事实。问答、讨论和原始文档是整理依据，
不逐轮、逐句或逐段直接追加为职业事实。当前工作以建立这一内容标准并整理存量为
目标，不以查明膨胀最早发生在哪次转换为前置条件。

以下是本轮确定的内容要求。现有存量已按此整理并通过条件保存发布，派生目录已同步，
同经历的重复入口已归并；原始资料、人工措辞及历史的保全和实际来源读取均已核对。
这些是本次数据整理的结果，不能仅由 JSON 格式或来源覆盖校验推定，也不代表
今后的自动语义整理、保存/导入约束或章节检索已经实现。

### 内容归属

| 内容 | 保存位置与用途 | 日常匹配读取 |
| --- | --- | --- |
| 经历主要内容 | 每段经历一份当前事实内容，按工作方向或子项目组织 | 目录选中后读取 |
| 补充详情 | 有独特事实的技术说明、实验细节、论文与产物 | 需要具体细节时读取 |
| 整理依据与维护记录 | 原始问答、讨论、来源原件、旧稿、更正历史、审核和操作说明 | 不作为独立工作证据默认展开；核对来源或处理实际冲突时按需读取 |

这些是内容职责，不要求另建数据库或复制原始资料。复用已有来源、关联材料和
不可变历史；责任、状态及范围仍随相关事实可用，不能因分层而丢失。

### 目录的筛选内容

目录默认筛选输入围绕“做过什么、涉及哪些技能与技术、解决什么问题”组织：
稳定经历 ID、技能与技术检索词、工作内容与问题领域短摘要，以及正文入口和对应版本。
同一经历聚合检索词，不为每个技能或每次讨论新建经历条目。

名称用于识别和展示；机构、日期等保留在完整经历中。它们不是每次相关性筛选的
必要输入，不因字段缺失或名称不相似排除经历。有明确机构、时间或年限条件时，
再按需读取适用字段；不因精简目录而删除完整经历中的这些事实。

责任归属、协助方式及计划/进行/完成状态同样保留在完整经历中，不是目录初筛的
必带字段或准入条件。目录负责发现相关内容；选中后读取正文，在匹配判断和写作时
使用适用责任与状态。目录命中不直接表示个人已独立完成或掌握相关工作。

技能检索词从已保存事实、明确自述及有上下文的有效详情提取，随所属经历一起更新。
仅在团队或关联产物中出现的技术，其对应归属保留在完整经历中，不能自动写成个人掌握。
检索词不代表熟练度评分，也不要求完成研究审核才能检索。工作内容摘要支持语义
发现，不能仅因缺少同名技能标签就漏掉相关经历。

本次存量目录已使用整理后的技能主题与工作摘要。完整的筛选字段投影仍是目标要求，
不改写下文当前存储契约；运行时对展示字段的交付调整仍需后续实现和验证。

### 经历主要内容

一段经历统一组织身份、机构、角色、时间与状态、背景目标、实际承担的工作、
方法与技术、合作责任、结果产物和必要的资料入口。未记录的字段可以留空；
不为补齐模板而编造事实。大型经历按子项目或工作方向分节，不按对话轮次分节。

工作方向按实际工作含义组织，不与仓库一一对应。例如，同一经历可包含后端、前端
和组织管理三个方向；文档与基础设施仓库可为其中多个方向提供来源，不因存在独立
仓库就自动新增经历或章节，也不从仓库存在推断个人责任。目录默认仍保留一个经历
条目，聚合其技能和工作摘要。仅在整理后主要内容仍明显过大时，再针对该经历细分
读取；普通经历不要求预先建立章节检索结构。

- 事实以一项可独立理解的工作或结果为粒度，可保留完整段落。只在时间、责任、
  状态或工作内容确有区别时拆开，不把每句话、每个操作步骤都变成独立事实。
- 合并同一经历、相同责任及时间范围内的重复表达，保留独特技术、数字、成果、
  限制和来源关联。不同时间、责任或状态的同文记录不能仅按文字相同合并。
- 项目身份、别名、来源关系、责任及状态放在对应字段或关联上下文；
  “保留所有来源”“仍需审核”等维护说明不作为工作事实。
- 用户自述和明确更正可以直接作为事实依据，无需重做研究审核或逐条确认。
  对话中的假设方案、提问、能力评语和推理练习不能转成实际完成的工作。
  实际职业计划若需记录，保留其计划状态，不改写为成果。
- 当前正文保留真实的个人与团队责任。AI/工具协助保存在内部归属记录，
  不把协助误写成个人独立完成，也不把内部工具说明平铺为职业成果。
- 学历等固定资料沿用已确认记录。重要事实冲突单独保留适用范围与待澄清项，
  不能把冲突双方都写成当前确定事实；只在实际需要时询问。

例如，同一次工作的“做了校验器”“增加输入检查”“实现输入校验”可整理为一条
有上下文的工作记录；如果另有不同阶段的性能优化及实测结果，则保留其独特事实。
“之后需要核对责任”属于整理记录，不能作为又一项工作成果。

### 经历、工作方向与共享事实的关联

以下是逻辑数据约束。本次存量整理复用当前事实 Schema，并用附属派生组织记录
保存工作方向和共享引用：

- 经历保留原有稳定 `experience_id` / `candidate_id` 绑定，改名、分节和资料移动
  均不新建经历身份。目录继续指向该经历及其对应版本。
- 每个工作方向有稳定身份并且属于一个经历。归属必须由嵌套存储或显式引用保存，
  不能只靠标题、文件路径或检索词推测；多个方向始终可还原到同一经历。
  同一经历的旧重复入口可按明确整理决定退出当前目录，历史来源仍可追溯；
  不强制为这些旧 ID 实现实时读取或中途任务接续兼容。
- 事实在所属经历内保存一份正文、事实 ID 及来源关联。工作方向通过事实 ID 引用，
  同一事实可关联多个方向；不同方向确有不同的工作内容或责任则保留各自事实。
- 程序校验工作方向的事实引用属于同一经历，且在对应版本中存在。跨方向汇总按
  经历与事实身份去重，不能把同一成果重复计算或重复交付；不同经历的同文事实
  不能据此自动合并。
- 修改共享事实只更新所属经历的一份事实内容，所有方向引用随该经历的新版本使用。
  分组调整保留事实身份；事实合并保留旧引用对应，历史申请仍可追溯原版本。

复用现有经历记录、来源引用和版本历史；JSON 嵌套即可表达这些关系，不新增数据库。
当前 `experience-facts/v1` 继续保存事实。此次工作方向、技能主题、事实引用和内容
版本绑定保存在附属 `experience-organization/v1` 派生记录中，使用材料角色
`generated`，不把组织索引当作新的事实来源。程序已在发布时校验关系归属；
不能把自由文本 `scope` 或经历标题当作关系键。

派生组织记录只对应本次固定内容版本，普通后续保存尚不自动维护它。运行时仍以
当前事实列表交付匹配资料；未实现分章节读取。未来扩展主契约或自动维护时须保留
明确版本绑定。保留同一经历的关联仍是迁移与读取的验收项。

### 存量整理与增量维护

先用单段经历形成整理前后可比较的候选，再按同一标准处理其余经历。保留稳定经历
身份、人工更正和原始历史。每项旧记录说明其去向：保留、合并、转入补充、转入
整理依据或保留为未决冲突。合并事实保留旧事实 ID 到新事实的对应，既有引用仍可
追溯其原版本，不能静默改绑为不同含义。该对应留在私人维护记录，不进入日常模型输入。

后续问答只提取新增事实或更正，更新所属经历；重复讨论只补充必要来源关联。
未改变事实的讨论不新增事实条目。系统操作说明和研究评估留在各自记录中。
日常检索消费目录、整理后的主要内容和按需详情，不再次展开所有整理依据。

验收检查独特职业事实、时间、责任、状态、来源及人工更正是否保全，重复和内部
说明是否退出默认事实输入，以及条目数与传输体积的变化。不能只凭数量变少、
Schema 通过或模型不再超限判定完成。不给每段经历规定任意事实条数上限，
也不按当前 JD、简历页数或请求预算删除独特职业事实。

## 当前记录契约

结构化记录使用 `schema_version=experience-record/v2`，主要内容放在 `content`，
不再并存另一份主要 `body`。`content` 使用 `experience-facts/v1`，包含：

- 稳定的 `experience_id`、`candidate_id` 和内容 `revision`。
- `title`，以及可空的 `role`、`organization`、`start`、`end`、`location`。
- `sources`：每个来源的 `id` 和 `locator`。
- `facts`：每条事实的 `id`、`text`、`source_refs`、`responsibility`、`status` 和 `scope`。

程序校验候选人及标题绑定、事实与来源 ID 的唯一性和引用归属，并计算内容版本。
更新不能改变 `experience_id`，也不能把结构化记录降回 `body`。外层记录版本与内容
版本各自保留含义；修改现有记录必须携带当前外层 `expected_revision`。

原有 `body` 记录及不可变历史仍可读取。新记录可直接保存 `content`；已有 `body`
记录必须通过下述显式导入转换，不能用普通 `save` 绕过覆盖校验。
来源覆盖记录 `migration` 由导入程序生成；普通 `save` 不能自行提交或修改该记录。

## 首次整理与后续同步

从系统 checkout 运行，将输出保留在私人上下文：

```sh
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' sync
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' directory
```

首次同步为未整理的经历建立兼容正文和目录入口。程序按源文档分节保留已保存的身份事实
及关联原文，不编造叙述、不按当前岗位筛选，也不要求研究审核或能力评分。
无可读取详情时保留已有身份内容和待补状态。读取失败不表示申请人缺少能力。

后续同步比较每个经历的记录及关联来源输入，只读取变化条目的来源。可用
`--candidate-id '<id>'` 限定条目；同一仓库关联多个经历时，不带该参数可识别各自变化。
库外仓库变更需先由既有来源操作器更新捕获及 manifest 绑定；本入口不扫描任意仓库。
改名、资料移动或机构变化不改变 `candidate_id`。

结构化记录同步时保留已保存的事实、标题及明确更正的元数据。来源变化只刷新关联
资料及输入版本，不把旧来源覆盖回主要事实。新资料或其文字、责任上下文发生变化时，
标记待导入；它们不会直接追加到默认事实输入。只改元数据或材料不能清除已有待补状态。

## 显式内容更正

`read` 返回当前 `content` 或兼容 `body`、元数据、关联材料、版本及上一版指针：

```sh
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' --candidate-id '<id>' read
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' --candidate-id '<id>' \
  --request '<private request.json>' save
```

结构化保存请求包含 `content` 和当前 `expected_revision`；新建还需 `title`，且不传
`expected_revision`。兼容旧记录仍可显式更正 `body`，但不能向结构化记录写入 `body`。
未记录字段不必补齐。可选 `metadata` 包含 `category`、`institution`、
`aliases`、`dates`、`status`、`related_ids`、`links`。未传入的已有元数据和关联保留。
显式编辑的元数据及正文优先于后续来源同步。

`materials` 可保存按需补充资料及来源/导出关系，每项含 `id`、`source_name`、`text`、
`role`，可附 `derived_from` 和原有定位、责任说明。角色含 `primary`、`supplement`、
`artifact`、`generated`、`history`。人工替换主要正文后，旧导入正文保留为历史；新关联
资料作为补充同步，后续变更更新对应补充项。旧来源不能恢复已被明确更正的主要事实。
纯简历措辞修改不调用此保存入口。

## 从旧正文显式导入 JSON

在同一个 CLI 中先预览，再发布：

```sh
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' --candidate-id '<id>' \
  --request '<private import-request.json>' preview-import
uv run --locked --offline --no-sync python -B scripts/run_career_experiences.py \
  --manifest '<private manifest>' --candidate-id '<id>' \
  --request '<private import-request.json>' import
```

请求使用 `schema_version=experience-import/v1`，包含当前 `expected_revision`、
完整 `content` 和 `parts`。每个 part 指向原记录的 `/body` 或 `/materials/N/text`，
提供 `start`、`end`、逐字 `quote`、处理类型及理由。范围使用 Python 字符位置，
不是 UTF-8 字节位置。`generated` 和 `history` 不属于本次事实导入范围。

处理类型为 `fact`、`presentation`、`duplicate` 或 `unresolved`。事实映射必须绑定
已交付的 `fact_ids` 和事实实际引用的 `source_ref`。每条新事实必须有直接事实映射，
每个事实与来源引用的组合都必须有对应映射。纯排版段不能声明事实覆盖；重复段必须
显式指向空白规范化后文字相同、事实相同且责任上下文一致的原事实映射。

预览不写库。程序检查原文范围、逐字内容、重叠、非空白遗漏及未表达项；未处理内容
出现在 `unresolved`，`ready=false` 时拒绝发布。程序不自动剥离 TeX，也不猜测原文
事实。原文逐段覆盖仅证明结构上的来源对应，不证明事实改写保持了完整语义。

`import` 再次校验请求，并通过现有比较后写入（CAS）发布。预览后记录有变化时，
陈旧 `expected_revision` 会被拒绝。成功后保存结构化内容、覆盖记录及前版指针，
保留原始资料和旧版；不会改写既有申请中的人工 TeX。

已有结构化经历收到新资料后，仍使用同一 `preview-import` / `import`。此次只映射
新增或变化的有效材料范围；已覆盖且上下文未变的材料不必重复映射。程序保留原有
经历字段、事实、来源定位及原引用；新增事实或新增引用必须有本轮来源映射。
已有事实的文字、责任、状态等更正走显式 `save`，不在资料导入时顺带覆盖。
每次导入记录前版，原覆盖记录仍可沿不可变历史追溯。

实际读取失败保存在 `metadata.unavailable_sources`。映射完成不会清除未读来源，
空映射也不能解除原因不明的待补状态。成功来源同步可以清除旧读取诊断；用户明确
更正事实可按原策略接管。重复提交相同内容或仅修改版本字段不算事实更正，不能
借此清空诊断。尚未映射的有效材料仍会保持待导入。

## 默认事实输入与历史材料

默认分析入口逐条读取结构化事实，携带事实 ID、内容及记录版本、责任、状态、范围
和引用上下文；不把原始材料文字重新拼接成事实。未转换的历史 TeX 保存在材料档案，
标记待导入，不进入默认事实输入。原有生成器在生成阶段仍可读取其兼容档案。

教育来源从已记录的 `profile_record` JSON 提供固定事实，并应用已确认的教育更正；
旧接受稿中的 `accepted_latex` 留在档案中。程序保留学位的在读状态，不从旧排版稿
推断已获学位。待补或来源不可用仍是显式状态，不表示申请人缺少能力。

## 去重、目录和历史

- 以规范化空白后的完整资料文本及其责任、任务、日期等上下文判重，保留所有来源 ID
  和源/产物关系。相同正文的个人与团队责任分别保留，并随按需来源一起交付。不同内容不因
  扩展名或近似措辞而合并；独有 PDF 批注保留。二进制 PDF 的文字须由既有提取接口或
  明确整理提供，本入口不猜测二进制内容。
- `generated` 和 `history` 不进入当前事实检索。生成简历及其 PDF 应在来源关联中明确
  标记为 `generated`；程序不根据文件名猜用途。其缺失不降低当前正文的可用性。
- 结构化目录摘要来自事实文字；检索词还包含经历元数据、责任、状态、范围及有效补充
