# 一次岗位解读与评分框架（P02）

普通岗位分析在读取申请人资料前，由 `application_job_brief.create_job_brief()`
仅根据完整 JD 生成并保存 `job_brief`。它包含业务对象、业务目标、工作产出、
方法用途、原子要求、原条件组关系、业务组权重及短理由。目标未说明时保留未知，
不从职位名、公司或孤立关键词补造职责、行业或盈利门槛。

检索、匹配、事实更新后的复核及写作上下文复用同一份说明。程序校验固定要求、
组关系、权重和版本；匹配输出不得更换岗位理解或要求。分经历写作者与终审收到
相同说明。本步不增加第二个岗位审核模型。

## 保存与接续

普通入口为 `analyze_job()` 的现有两库检索流程。首次分析在分析版本目录的
`job-brief/` 中保存输入、Schema、提示词、模型原始结果、尝试记录和
`job-brief.json`。这些文件属于私有工作空间，不提交真实 JD 或模型输出到公库。

同目录已有有效结果且岗位输入相同时，直接复用，不再调用模型。读取前检查完整性、
岗位绑定、大小和符号链接。原尝试目录不覆盖、不隐式重试。

J04 已将恢复接入现有 `analyze_job(..., resume_from=...)` 和 Flow 显式重试：

- 同输入的原 P02 已成功时，校验并采用原 `job-brief.json`。P03 或 P04 失败不再解读 JD。
- P02 原响应已保存但结果未发布时，核验原输入、提示词、Schema 与响应绑定后本地采用。
- 当前阶段有明确失败结果时，显式重试建立新尝试；原目录及失败记录保留。
- 已发出调用却没有可核验结果时，返回 `match_result_needs_recheck`。先核对原调用，
  不因新目录或新请求 ID 盲目重放。

Flow 保存失败尝试与新尝试之间的 lineage。只有输入绑定一致才接续原分析；输入
变化不能伪装成阶段恢复。事实更新复核显式传入原 `job_brief`，沿用固定岗位框架。
模型配置或申请人资料变化本身不会重写这份说明。恢复与已完成分析的复用边界见
[阶段恢复](career-library-retrieval.md#阶段恢复与已完成分析复用)。

岗位输入绑定包含公司、职位、地点及完整 JD。传入另一岗位的说明或更改固定结果会
报错。旧分析及未接两库的历史底层 API 保留旧契约；不把旧记录静默转换为新框架。

## 计分规则

业务组由首次模型解读提出整数权重 `1..100` 和理由。程序归一到总计 100 分。
`required`/`preferred` 继续表达 JD 性质，不强制套用旧 3:1 比例。

| 原组关系 | 组内分值 | 硬性资格判断 |
| --- | --- | --- |
| `all`（各项均需满足） | 原子项区间端点的均值 | 任一明确不符则冲突；全部支持才支持 |
| `any`（任选一项） | 原子项区间端点的最大值 | 任一支持即支持；全部明确不符才冲突 |
| 复合 OR 分支，每支为 AND | 先取各分支内均值，再取分支最大值 | 任一分支全部支持即支持；每支都有明确不符才冲突 |

2026-11-04 起，首次解读不再把同一条件的多种满足方式拆成原子项：如"硕士或博士"、
"Python 或 Java"各为一个要求，文字保留"或"，由匹配判断是否满足其一；只把各自都需要的
不同能力拆开，新解读使用 `all`。解读须覆盖 JD 写明的全部职责与任职要求（学历、知识、技能、工具、经验、个人特质），
不因看似次要或与职责重叠而省略。引用须为原文连续一段（整句或整条）；模型若用省略号连接
片段，各片段须按原文顺序出现在同一段内，程序将引用还原为首片段至末片段的原文。
下列 `any` 与复合分支规则保留用于读取旧解读。

复合关系使用原子项的零基索引，例如 `(A AND B) OR C` 为
`alternatives: [[0, 1], [2]]`；`(A OR B) AND C` 为 `[[0, 2], [1, 2]]`。
不新建通用表达式语言。空分支、越界引用、未用原子项及被其他分支吸收的冗余分支拒绝。

原子项由模型在判档范围内给出满足度 `fit_score`（2026-10-31 决定）：`supported` 75–100、
`partial` 30–75、`unknown` 0–15、`gap` 0；程序截到所属档内并按 5 分取整，原子项取单点。
资格判断仍只看判档。引用被扣下的项保留 `[0, 模型原满足度]`，资料未读完的未知项保留 `[0,1]`。
没有满足度的旧分析沿用 `supported` `[1,1]`、`gap` `[0,0]`、`partial` 半分、`unknown` `[0,1]`。组区间乘归一权重后相加。现有 `coverage` 字段表示
`100 - (upper - lower)`，它是该框架的已确定分值范围比例，不是已读文件比例，
也不是简历选材覆盖率或概率置信度。全部结果确定时上下限相同。

精确归一后的重复原子项在同组内合并；相同组不重复计分。不同组重复使用同一要求
会拒绝，避免重复加权。语义同义合并由首次解读负责；程序不能证明任意措辞语义相同。
拆分增加原子项不会增加原组总权重。完整框架、全部原子项及其元数据必须同时到场，
丢项、重复项、改权重或改关系不能产出部分伪完整分数。

资格与数值分开。只有 JD 明列的不可协商就业资格或证件条件才标记硬条件；普通
职责或技术经验不因写着 required 就自动成为淘汰门槛。语言等级要求不是硬条件，
每种语言等级各作一条计分要求，未达到只降低匹配分（2026-11-08 决定）。流程及解释按原组关系汇总，
保留各分支事实、人工说明和历史。

本步沿用现有“无数值自动跳过”策略，不增加低分阈值：硬资格明确冲突为 `hold`，
资格未明或区间未收敛为 `needs_input`，其余为 `matched`；`auto_skip` 始终为
`false`。该策略随分析结果保存，不替代 P04 后续完整匹配与路由工作。未知造成下限
较低不能自动跳过岗位。

## 固定样例与验证范围

合成 Quant Research 样例把金融业务产出组设为 80、数学/Python 方法组设为 20。
直接业务经历支持前组时得 80；只有方法词匹配时得 20。业务组拆成多个子项、重复
JD 句子或增加同内容资料均不增加该组总权重。未知方法项得到 80–100，而不是
因低下限自动跳过。JD 未列的实盘经历、盈利结果及财务表现不加入硬门槛。

80/20 是验证框架行为的固定工程样例，不是所有 Quant 岗位的固定权重，也不表示
已校准就业预测能力。实际权重来自对应完整 JD 的一次解读。Schema、引用与哈希
检查仅证明结构、引用存在和固定输入完整性，不证明业务解释或语义判断正确。

本轮仅用录制/合成 runner 验证源码；未运行真实岗位模型、私人资料整理或真实 ATS。
J04 已接入现有读取、匹配及阶段恢复；完整写作、Prism/ATS 接续与申请内容存储仍按 J05–J08 推进。
