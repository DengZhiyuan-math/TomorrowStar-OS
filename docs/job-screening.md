# 岗位匹配与投递分流

## 当前产品规范 — 2026-10-20

完整流程见[单岗位流程](single-job-flow.md)，实施顺序见[开发计划](development-plan.md)。
系统处理工作平台通过邮件推荐的岗位，不自行扩大到自动搜寻。推荐持续增量收录，
不设邮件数或岗位数限制；完整 JD 在岗位轮到处理时读取，直接复用现有登录态。

| 分流 | 处理方式 |
| --- | --- |
| 高价值、高匹配 | 先自动完成岗位分析、针对性完整简历与必要材料初稿，再提示用户精准调整。用户一次继续后接续填写。 |
| 匹配一般 | 系统自主完成材料、填写和上传，停在最终 Submit 前。 |
| 分数过低 | 自动跳过并记录原因，不生成申请或要求人工确认低分。 |

系统结合匹配分数和已有偏好作判断，不要求用户逐岗填写一套投递前评价。
未知公司偏好、未知薪资或部分条件不满足，本身不构成等待人工的理由。
匹配分用于投递决策，不能当作 Skill 掌握程度或录用概率。
沿用已有合理评分规则；具体阈值与价值信号的实现差距由开发计划核对，不能在文档中虚构已实现的数值。

只有重要必要事实缺失、实际重要冲突、登录验证、操作超时、持续无进展或结果不明时，
停止当前岗位等待用户。不得自动转到其他岗位，也不集中积攒问题；新邮件仍可收录。
用户可选择跳过并以后恢复。高价值岗位不会因为需要人工精准调整就被排除在材料准备之外。

## 资料与判断

职业经历事实以职业经历库为准；信息库提供申请信息、可复用答案与零碎信息。
用户明确补充或更正事实直接入对应库，保留来源和历史。系统判断答案适用范围和题意，
不用固定问题别名或预审语法限制自主能力。重要语义确实不明确才问，一般动机文案自行生成。

保留岗位身份、已投递记录和可恢复跳过记录，避免重复申请。相同链接、ATS 岗位 ID、
跟踪参数及已知路径别名可供系统识别。同公司不同岗位不自动视为重复；缺少身份信息时先用
已有上下文判断，确实无法确定且影响投递时才询问。学历、语言及其他资格只影响相应判断，
未知条件不应阻止整份材料准备。已有事实直接复用，不重复询问学历。

适配器只是执行选择。缺少平台适配就使用通用浏览器，不因平台名单、逐请求许可或普通多步页面而停。
人工修改优先保留，事实变更只更新受影响内容，模型配置变化不使有效分析失效。
最终 Submit 由用户操作；系统识别明确成功页面或确认邮件后更新记录并继续下一岗位。

## 现存实现参考与差距

下列描述供维护现存 `job_screening.py` 和旧入口，不是新的产品审批要求。
本次只修改文档，没有改变这些代码、安装版或历史验收结论。

- 旧列表提供 AI/ML、量化及各项人工评价，按保存的 `application_strategy` 和重点信号分流。
  当前自动 pipeline 没有完整接入这套高价值 route，仍会选择最高匹配岗位自动准备填写。
  产品需要接通分流，不能要求用户逐项填评价来弥补。
- 旧 `worker_preparable` 同时检查准备状态、重复、截止日期、有限平台和法/德语规则。
  这些可作为资料提示与执行事实，不能把旧平台支持列表提升为投递边界。
- 旧语言复用读取 confirmed、全局、无冲突 CEFR 记录；有限正则识别明确最低等级，
  问题复用主要靠固定别名。未识别语句和选项不等价目前可能触发提问，需改为系统判断。
- 旧执行器的多个阶段重复检查 revision、历史和材料，有的要求用户确认已提交并另填接收来源。
  新流程保留自动一致性检查，合并重复人工步骤，并自动记录明确提交结果。
- 列表搜索继续可使用 Unicode NFKC 和大小写归一化；搜索与技术可准备提示均不是能力评估。
