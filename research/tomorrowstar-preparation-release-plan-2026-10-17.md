## 1. 交付目标与第一版边界

交付一个单用户、本机运行的材料准备入口：

```text
点击更新推荐
  → 有界增量读取邮件、提取岗位、去重、获取公开完整 JD
  → 按明确偏好和资格条件初筛
  → 对候选逐岗分析，生成可解释的分级和排序
  → 按本批选择的范围生成专用简历
  → 集中审核原文、改写差异和 PDF，保留各版本
```

首版建议：

- 保留现有 LinkedIn / Indeed 推荐来源；时间窗口可配置，默认近 7 天，后续按已持久化进度有界更新。
- 每批默认最多分析 20 个候选，沿用现有规模，串行执行。达到限制时明确显示剩余工作和继续入口，不声称读完全部邮件。
- Gmail 只读；不保存邮箱凭据。沿用现有 Codex connector，不另建 OAuth 邮件客户端。
- 一次确认方向、地区、远程偏好、职级、语言及按国家适用的工作资格等已有事实。未确认项保持未知；不编造偏好、薪资或资格。
- 以现有英文 A4 简历为输出范围，补质量检查，不新做任意模板编辑器。
- 用户可一次启动本批分析和所选等级的简历草稿生成；每份简历仍单独保留审核状态。生成完成不等于材料批准或已申请。

暂不纳入：定时无人值守运行、全邮箱历史迁移、更多来源平台、浏览器登录态抓取、ATS 填写／上传／提交、招聘者联系、完整 Grill-Me／Skill 图验收、模板市场或新数据库。定时运行属于后续独立需求，本计划不创建自动化。

## 3. 分级规则：先排除，再排序

等级代表材料准备建议，不代表录用概率或经过 Grill-Me 证明的个人能力。

| 结果 | 建议定义 | 默认后续 |
| --- | --- | --- |
| A：优先准备 | 无已知硬条件冲突，关键资格有依据，目标方向／偏好匹配，有直接相关材料支撑 | 本批可自动生成待审核简历 |
| B：可以准备 | 无已知硬条件冲突，有相关材料；部分加分项不足，但不影响已知必需条件 | 用户可在本批范围中选择生成 |
| 待确认 | 完整 JD 不足，或关键资格、来源事实有未决冲突／未知 | 集中列出问题；不自动标为可申请 |
| 暂缓／排除 | 已确认硬条件冲突、明确偏好排除、重复／过期／已有进度，或当前材料明确不足以支持准备 | 保留具体原因与来源；不自动生成 |

补充规则：

1. 缺少来源不等于用户没有能力；未知不能自动降为不符合。
2. 非关键薪资或公司偏好未知，不把所有岗位都卡在待确认。硬资格与可选偏好分别处理；未提及条件也不伪装成已满足。
3. 平台无法自动填写不影响材料价值。准备状态与旧 worker compatibility 字段分开。
4. A/B 同等级可按资料支持、目标偏好、完整性和时效排序。具体政策版本和排序理由必须显示；分数阈值若使用，需用用户复核样本校准后再冻结。
5. 人工调整保留理由与政策／输入版本。调整优先级不能静默抹掉资格冲突；确认新事实后再更新资格结论。
6. 待确认岗位可由用户明确要求生成带未决标记的草稿，但仍不能称为已符合申请条件。

## 4. 开发顺序与工作包

以下是待实施工作包，不是已完成票据。先形成一条可演示的纵向流程，再扩充异常处理；每阶段保留明确验收。

| 顺序 | 工作包 | 产物和验收点 | Codex 主动耗时估算 |
| --- | --- | --- | --- |
| 1 | 仅准备材料模式与就绪检查 | 原生入口不启动新 worker；Gmail/Codex/资料/PDF 能力独立显示；没有 Cua 权限也能准备材料；旧运行保持原状态 | 1–3 小时 |
| 2 | 增量拉取与来源队列 | 有界分页及私有 checkpoint；消息／岗位防重；达到上限仍有明确剩余位置；异常后不跳过未处理项 | 4–7 小时 |
| 3 | 偏好、初筛与分级 | 一次配置偏好；复用逐岗分析和资格状态；等级、证据、未知项及排序理由可复核；输出不依赖 worker 支持的平台 | 4–8 小时 |
| 4 | 批次编排与集中审阅 | 现有任务之上的薄清单；串行；单项失败隔离；暂停／取消／继续／仅重试失败项；可批量选择生成范围 | 4–7 小时 |
| 5 | 简历质量与导出恢复 | 当前来源对当前改写的数字／日期／技术词差异提示；空材料诚实停止；校验后的草稿 checkpoint；PDF 失败只重试导出；原文、差异和版本同屏审核 | 4–7 小时 |
| 6 | 安装版、故障与真实批次验收 | 相关回归和完整默认离线；安装版隔离流程；真实只读推荐及小批简历审核；保存覆盖、耗时、重复调用和人工修改量 | 6–10 小时 |

依赖：`1 → 2 → 3 → 4 → 6`，`3 → 5 → 6`。2 与 5 的独立实现可部分并行；共享任务存储、UI 整合和安装验收串行收敛。不能把子代理人数作为工期除数。

第一轮贯通优先使用小批样本：读入 → 分级 → 生成至少一份待审核 PDF。此时只是内部可演示版本；批次重启、幂等、来源失效及真实审核通过后才称稳定可用。

## 5. 稳定可用的验收门槛

工程验收：

- 同一批连续刷新、重复点击与重启后，不重复创建岗位或采用多份同输入材料；每个已处理候选有可解释的终态，未完成范围可见。
- Gmail 断连、单个 JD 获取失败、模型失败、PDF 失败分别有独立状态。一个岗位失败不阻塞整批；只读获取可有界重试，模型任务不因重开 App 被隐式重跑。
- 模型超时但结果未知时，先保留 attempt 并核验；不承诺跨进程崩溃下模型计费严格 exactly-once。已验证的成功草稿可供显式导出重试复用。
- JD、职业资料、偏好、规则或模型配置变化，只失效受影响的派生结果；旧 PDF、原文、审核记录和失败证据保留。
- 资格冲突与未知始终可见；缺完整 JD 不能伪装完成分析；空相关材料不能伪装完成岗位专用简历。
- 数字／技术词检查通过不等于语义无误。每条改写绑定自己的来源，不能用简历其他经历替本条授权事实。
- 安装版验证本地 headless PDF 导出、长文本／长链接／中英文姓名、分页、可读文字和无裁切；不把 mock PDF 通过写成真实导出通过。
- 在隔离工作区至少连续 3 次安装版冷启动完成本地 PDF 生成／预览／正常退出；模型完成、导出和结果采用附近的退出竞争分别注入验证。历史未归因故障继续保留，不能把新路径通过写成历史根因已修复。
- 新准备入口没有 ATS 导航、填写、上传或发送动作；不恢复旧暂停任务，不改变申请进度为已投递。

建议真实试用样本（验收设计，不是现有覆盖承诺）：

- 20–30 个实际推荐岗位，包含符合、冲突、未知、重复及页面不可取得等不同情况；无法取得全文也计入覆盖报告。
- 5–10 份针对所选岗位的 PDF，逐份人工检查事实、选材和版面。
- 至少 3 个独立更新批次，覆盖重复拉取和新增邮件；另用隔离故障注入验证中断及选择性重试，不在私人正式进程上制造故障。
- 单独记录邮件读取范围、全文取得率、分级修正、草稿完成／失败／复用数、总耗时、模型调用和实质性人工修改。没有真实分母前不报“90% 自动化”或每份固定分钟数。
- 最后一批应无需开发者排障即可完成所有岗位的成功或明确异常归档；正常用户工作只剩事实澄清、候选选择和材料审核。

质量验收需要用户确认偏好和真实事实，并判断简历能否代表本人。纯 Codex 开发指不需要人工写代码，不等于免除这些业务判断。

## 6. 工期口径与风险

以当前代码为起点，假设 GPT-6.1 Sol Fast、额度充足、允许有限并行、已有 Gmail 连接和职业资料可用：

- 工作包逐项估算约 23–42 小时，排期建议取整为 **25–45 个 Codex 主动工作小时**。
- 包含读代码、实现、工具执行、测试、打包、安装路径核验、审计和正常修复。不是人类工程师工日，也不是纯 token 生成时间。
- 若 Gmail 分页证据、原生中断或系统 Chrome PDF 启动出现额外修复循环，保守准备 **40–60 小时**。这是风险情景的总量，不能再叠加到 25–45 小时上。
- 按每天实际运行 8–10 小时，正常约 **3–6 个工作日**；风险情景约 **5–8 个工作日**。账号连接、额度恢复、用户事实确认和质量审核的等待会延长日历时间。
- 这些是基于工作包的工程估算，不是已测得的 Sol Fast 生产率。官方确认 Fast 支持 GPT-6.1 Sol，但未给该模型一个可用于项目排期的固定提速倍率。[OpenAI Docs：Speed](https://learn.chatgpt.com/docs/agent-configuration/speed)

主要风险及收敛方式：

1. connector 有分页参数，不等于当前严格事件验证 adapter 已支持；先用合成 search/read 页记录验证，再做真实只读路径验收，未完成页不推进完成水位。
2. [原生生成中断票 27](../.scratch/single-job-application-flow-2026-10-16/issues/27-native-interruption-recovery.md)仍与本范围相关。复用现有 attempt／恢复逻辑，只排查材料准备路径；无法归因的历史事件继续如实保留。
3. Chrome 无头 PDF 启动需单独验证；不能把 Cua 观察或 ATS 网络问题都算作 PDF 根因，也不能因取消投递而忽略本依赖。
4. 分级边界以用户实际偏好和代表性样本校准。先做透明分流，不做招聘成功率预测或复杂评分研究。
